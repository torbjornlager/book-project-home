Proof-of-concept implementations

The proposals in the book manuscript are accompanied by executable proof-of-concept implementations. These serve complementary purposes: the Trinity demonstrator makes the ideas accessible through tutorials and interactive examples; the node implementations explore their realization in different Prolog systems; and the simple nodes expose the core mechanisms in code small enough to study alongside the book.

A separate Trinity conformance suite tests observable behaviour through public interfaces. Its current coverage matrix records selected language and protocol checks, interoperability results, and remaining differences across native SWI-Prolog, Trealla Prolog, GNU Prolog and the browser runtimes. The recorded results are encouraging: all selected required and supporting checks in the consolidated matrix pass for their tested configurations. SWI-Prolog and Trealla exchange actor messages and run remote queries in both directions; the selected HTTP query, paging and promise tests also pass in every direction between SWI-Prolog, Trealla and GNU Prolog. Separate diagnostics and experimental text checks still expose differences. These results describe specific tested revisions and facilities, rather than complete language conformance or production readiness.

The implementations also make the proposals tangible through executable examples. The SWI-Prolog and Trealla nodes run shared tutorial and code examples, including distributed interactions between them, while the browser runtimes provide another way to explore the actor language. GNU Prolog and Ciao support query examples within their narrower scope. Coverage therefore varies with each implementation's facilities; Ciao has not yet been included in the shared conformance matrix.

The implementation work has been done in cooperation with several AIs.

1. The Trinity demonstrator

The Trinity demonstrator is the interactive companion to the book. Readers can run queries against live nodes, spawn actors, explore statecharts and make remote procedure calls between nodes. Tutorials, examples and a shared language manual connect these experiments to the book's proposals.

The demonstrator brings together the browser interface and integration with browser-based and native nodes. Its native SWI-Prolog node and SWI-WASM browser runtime are now maintained in separate repositories, described below. This separation allows the demonstrator and the node implementations to develop independently while sharing the same language and protocols.

The hosted demonstrator has best-effort availability and may occasionally be unreachable.

2. The nodes

The node implementations explore how different Prolog systems can expose common query and actor interfaces, both in native processes and in the browser. Their scope varies: SWI-Prolog, Trealla and SWI-WASM support actors, while GNU Prolog targets ISOBASE and the Ciao Prolog prototype concentrates on paged queries over a resident database. The conformance suite compares the facilities each implementation supports.

2.1. The SWI-Prolog node

The SWI-Prolog node is the most developed implementation and the principal implementation supporting the book. Extracted from the Trinity demonstrator, it can now be loaded and tested as a standalone package.

Its layers provide local actors, selective receive, links and monitors, private source contexts, resumable toplevels, generic servers, supervisors, statecharts and parallel execution. HTTP supports remote queries, promises and yield; WebSocket connections support distributed actor operations. The node layer adds public profiles, authentication, execution policies and resource controls. Individual lower layers can also be used independently.

2.2. The SWI-WASM browser node

The SWI-WASM browser node runs Web Prolog in the browser using SWI-Prolog compiled to WebAssembly. It supports actors, private query sessions, paging, monitors and statecharts, together with HTTP remote queries and WebSocket communication with native nodes.

Extracted from the Trinity demonstrator, the runtime can now be packaged, tested and used independently. Its primary execution model places actors in Web Workers; an alternative main-thread model provides access to the browser's document. Local execution requires no running Prolog server, while distributed examples connect to remote peers.

Try Trinity Studio in your browser: an experimental IDE-style interface with a source editor, resizable workspace, example programs, paged queries and separate answer and output views. It uses the SWI-WASM node locally in your browser and needs no installation, account or running Prolog server. Use “Save source” to keep your work before reloading or closing the page. The Studio source and local setup instructions are also available.

Try The Genealogist in your browser: explore a family diagram, ask Prolog queries and add or remove relationships. This separate UI experiment uses the SWI-WASM node and needs no installation, account or running Prolog server. Each page has its own family database; use “Save Prolog” to keep changes before reloading or closing it. The experiment’s source and local setup instructions are also available.

2.3. The Trealla Prolog node

The Trealla implementation began as a port of the simple SWI-Prolog node and has grown into an independent ACTOR-capable node. Alongside actors, private source contexts and resumable toplevels, it now implements generic servers, supervisors, parallel execution and SXML statecharts.

HTTP provides remote queries, promises and yield, while persistent WebSocket connections support remote actor creation, messaging and toplevel control. Shared conformance tests exercise selected behaviour and interoperability with SWI-Prolog. Authentication, policy enforcement and resource governance are included, although runtime differences and deployment limitations remain documented work.

2.4. The GNU Prolog node

The GNU Prolog implementation targets ISOBASE, with ISOTOPE a possible later extension. A small C HTTP server supports submitted source, a shared database, JSON bindings, Prolog-text answers and paged query execution. HTTP(S) clients provide remote procedure calls, promises and yield.

Each active query runs in a separate operating-system process, preserving bindings and choice points between pages. Supervisors manage deadlines, resource bounds and cleanup. This design accommodates GNU Prolog's query interface and lack of general heap garbage collection. Selected HTTP interoperability tests include SWI-Prolog and Trealla; broader conformance, compatibility and isolation work remains open.

2.5. The Ciao Prolog node

The Ciao prototype explores a smaller part of the node interface: an HTTP endpoint that evaluates queries over a static, node-resident database and returns paged Prolog-text answers. Ciao engines preserve suspended computations between requests.

Queries execute through a database module using Ciao's pure package, restricting the predicates available to submitted goals. This provides a useful boundary but does not bound execution time or memory use. The prototype does not currently provide actors or JSON answers, and complete ISOBASE conformance has not been established.

3. The simple nodes

The book's implementation appendix develops small nodes to explain the mechanisms behind the larger implementations. The runnable simple-node repository accompanies this presentation with local actors, resumable toplevel processes, an HTTP endpoint with continuation caching, and an RPC client.

The emphasis is on readable code and experiments that readers can reproduce. Regression tests cover actor behaviour, HTTP paging, term transfer and cleanup under interruption; companion checks also exercise the appendix listings.

These teaching implementations run trusted local code. Actors share the host database, and the examples omit authentication, sandboxing, private actor databases and distributed actor transport. They provide a starting point for understanding the mechanisms and exploring ports to other Prolog systems.
